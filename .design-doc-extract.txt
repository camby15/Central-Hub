Overview and architecture
Figure 1. Central Hub architecture (dashed lines are scheduled or background flows)
Each site only knows two things: the hub address and its own API key. A customer fills the support form, the site sends it to the hub API, the hub saves the ticket, then queued jobs email you and the customer. You manage everything from one Filament dashboard, and the customer follows progress on a status page.

Django
A helper function plus a view. Keep the key in settings / environment variables.

Plain HTML
For static sites with no backend: a normal form posting to a hub endpoint that redirects back to a thank-you page. Add a honeypot field and a captcha.

Two kinds of key: The secret key stays on the server (Laravel and Django). The public key is safe in browser code because it can only create tickets, only from allowed domains, behind rate limits and captcha.

Cross-site Activity & Audit Logs
Every connected site reports to the Central Hub who was on it and what they did. The hub stores these events append-only and hash-chained, so they can be shown later as proof of who logged in, from where, and which records they changed.
Rule of thumb: Log on the site, store and prove on the hub. A site can send events but can never edit or delete them once they reach the hub.

How sites send logs
Laravel package
A Composer package (mbaram/central-hub-client) installed on each Laravel site. It listens to auth events, adds a middleware for requests, observes models, and queues batches to the hub. It can reuse spatie/laravel-activitylog for model diffs and forward those rows.

Django
A small Django app (hub_client) with a middleware, signals for auth and model changes, and a Celery or RQ task that sends batches.

JS snippet
For page views, time on page and static sites. Sends small batches with navigator.sendBeacon using the public key; the hub accepts only page.view and session events from this key, from allowed origins.

1.  Capture — Listeners, middleware and observers build an event with a uuid and UTC timestamp.
2.  Buffer and queue — Events are buffered per request and sent by a queued job, so the site never waits on the hub.
3.  Batch and sign — Up to 500 events per request, body signed with HMAC-SHA256 using the site's secret, plus a timestamp header.
4.  Retry — If the hub is down, the job retries with backoff; a local fallback table keeps unsent events.
5.  Ingest — Hub verifies signature, ignores duplicate uuids, adds geolocation, computes the hash chain, stores rows.

Tamper-proofing
Item
Details
Append-only
The Eloquent model throws on update and delete; no admin screen offers edit or delete for log rows.
Database permissions
The app's DB user has only INSERT and SELECT on log tables; partition drops run under a separate maintenance user.
Hash chaining
Each row stores row_hash = SHA-256(prev_hash + site_id + uuid + occurred_at + payload), chained per site; changing or removing any row breaks every hash after it.
Daily anchor
The last hash of each day is saved separately and in the evidence export, so the chain can be checked against an outside copy.
S3 Object Lock export
A nightly job writes the day's logs as compressed JSON to an S3 bucket with Object Lock in compliance mode (e.g. 7 years), so not even the account owner can delete them early.
Verification
A scheduled logs:verify command re-computes chains and raises an alert on any mismatch.
Privacy and compliance
Item
Details
Ghana Data Protection Act, 2012 (Act 843)
Register with the Data Protection Commission as a data controller, collect only what is needed for security and accountability, and keep it secure.
Notice and consent
Each site's privacy policy and staff terms say that activity is logged, why, and for how long; a cookie banner covers page-view tracking for visitors.
IP masking option
Per-site setting to drop the last octet of IPv4 (or last 80 bits of IPv6) for visitor page views, while keeping full IPs for staff and admin actions.
Retention policy
Page views 90 days, sessions and logins 12 months, audit events 5–7 years in the vault, then deleted automatically.
Access and requests
Only superusers and auditors can see logs; viewing and exporting logs is itself logged; process access requests from data subjects.
Data minimisation
Sensitive fields stripped by the SDK deny-list before leaving the site.
Have a local lawyer confirm the retention periods and wording for your sector before relying on the logs in a dispute.
Hub screens for logs
Item
Details
Activity Timeline
Live feed across all sites; filter by site, user, date range, event type, IP or country; click to open the request with all its events.
Audit Logs
Table of create/update/delete and permission events with a side-by-side diff of old and new values, plus a chain-verified mark.
User session history
For one person: every session per site with login time, logout time, duration, IP, device, location and pages visited.
Record history
Open any record (e.g. Product #88) to see every change to it over time.
Evidence export
CSV for analysis, or a signed PDF report with filters used, row hashes, daily anchor and export time, for disputes or audits.
Security alerts
Via Notification Center: 5+ failed logins in 10 minutes, login from a new country, admin actions outside working hours, mass deletes or exports, permission escalations, a site that stops sending logs.
Dashboard tiles
Logins today per site, failed logins, active sessions now, alerts open.
Build roadmap
1.  Phase 1 — Core hub (week 1–2) — New Laravel 12 + Filament project, invite-only staff login with 2FA, roles, sites registry with keys, tickets and replies, POST /api/v1/tickets, agent ticket list and ticket detail screens. Milestone: fragrance store sends a real ticket.
2.  Phase 2 — Real helpdesk + logging foundation (week 3–4) — Categories, assignment, attachments, SLA timers, email notifications, saved views and bulk actions, canned replies, settings screens, light and dark themes. Create site_activity_logs, site_sessions and login_attempts with partitions, hash chaining and POST /api/v1/logs/batch.
3.  Phase 3 — Connect every site + customer portal (week 5–7) — JS widget, HTML form endpoint, captcha and rate limits; customer portal with submit, track by ticket ID + email, and knowledge base; Laravel package with auth listeners, middleware and observers; Django middleware and signals; JS page-view snippet. Milestone: all sites send tickets and activity logs.
4.  Phase 4 — Audit screens and evidence (week 8–9) — Activity Timeline filters, Audit Logs diff view, user session history, CSV/PDF evidence export, S3 Object Lock nightly export, logs:verify command, privacy notices and retention jobs.
5.  Phase 5 — Site management and alerts (week 10–11) — Uptime checks, SSL expiry, heartbeat endpoint, site health screen, suspicious-activity alerts in Notification Center.
6.  Phase 6 — Polish (ongoing) — Analytics, canned replies, reply by email, Slack/WhatsApp alerts, knowledge base, multi-language widget, new modules from the backlog.
